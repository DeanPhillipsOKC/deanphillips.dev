This is part 1 of a series about the AI agents that build [RepBunny](/blog/ai-delivery-team/), a strength training app I work on around a full-time job. The [overview](/blog/ai-delivery-team/) covers the whole setup in a few minutes. This part covers the front of the pipeline: what goes into the backlog, and who works on it.

## Ideas go in rough, specs come out ready

Most of my ideas show up at the gym or in a meeting, so I file them from the GitHub app as one-liners. "Rest timer should buzz on the watch." That's not something an agent can build reliably.

A `refine-backlog` skill fixes that. It finds issues that haven't been scored yet, reads the code they'd touch, checks for duplicates, and rewrites each one with a clear problem, acceptance criteria, and the files involved. Then it labels it with an effort score and a value score, each on a Fibonacci scale (1, 2, 3, 5, 8, 13). Value divided by effort is the ROI, and ROI decides what gets built next. If it hits a question only I can answer, it [asks me from my phone](/blog/ai-delivery-team-asking/) instead of guessing.

## Reviewers fill the backlog too

Not everything waits for me to think of it. Six review agents run once a month, each playing a different role, plus a seventh routine that watches for anything about to expire:

- **Security audit** looks for secrets in the code and git history, vulnerable dependencies, and loose permissions in the build pipeline. It also checks that no change has started sending workout data off the phone.
- **UX review** drives the app, takes 80 or so screenshots across the main journeys, and files real usability problems.
- **Product review** compares what's shipped against the brand guide and roadmap and files missing features.
- **Accessibility review** checks every theme for contrast and tap targets, and runs the app with large text on a small phone to find anything that overlaps or gets cut off.
- **Help review** compares every feature in the app against the how-to guides on repbunny.app and files the gaps.
- **Process review** acts like a DevOps engineer looking at the delivery system itself. It has [its own post](/blog/ai-delivery-team-process-review/), because it keeps paying for itself.
- **Expiry radar** isn't a reviewer. It watches certificates, the domain, and app store deadlines, and opens a checklist for me when one gets close.

Everything a reviewer files comes in with a `status:needs-review` label. The builders can't see it until I remove that label. Reviewers are good at spotting problems and only fair at deciding which ones matter, so I keep that call.

## Lanes, so cheap work goes to cheap models

Early on I ran one agent in a loop on my laptop. It worked, but it meant the laptop had to be on, and every task got the most expensive model whether it needed it or not. Now the backlog is split into lanes, and each lane has its own cloud routine.

  <b>Dispatcher:</b> a GitHub Actions workflow with no AI in it. When an issue closes, and every two hours, it checks each of the 7 lane and model pairs. Work waiting and nobody busy? It fires that pair's routine. Otherwise it does nothing.

The dispatcher is the part I'm proudest of, mostly because it's boring. It's a short Node script. It costs about one free Actions minute per run and zero AI usage. An empty backlog costs no AI usage at all, and a lane starts its next issue as soon as the last one ships.

Lanes run in parallel, so two agents can be running the test suite at the same moment. Each lane gets its own isolated test data, so they don't trip over each other.

The cutoff between models moved once already. Effort 5 used to go to Sonnet. Then I started asking every build run to also decide whether its change needs a [manual check on a real phone](/blog/ai-delivery-team-gate/), and a mid-sized change plus that judgment call felt like too much for the cheaper model. Effort 5 and up now goes to Opus. It was a one-line change in the picker script.

## What broke

- **The schedule never fired.** I first ran the dispatcher hourly on a cron. In its first five hours GitHub never ran it once, because scheduled workflows get delayed or skipped when GitHub is busy. Now it runs when an issue closes, plus every two hours to pick up new issues and anything it missed. It used to run when an issue opened too, but at about 31 new issues a day that became the biggest cost in Actions minutes.
- **A run worked the wrong issue.** An early dispatcher marked the issue `in-progress` before starting the agent. But the agent's own picker hides in-progress issues, so it skipped the one it was sent for, built a different one, and left the first claim stranded. The fix was a separate `dispatched` label the picker knows to put first.
- **Cloud sessions see a smaller GitHub.** The proxy in cloud sessions refuses GraphQL and search, which is what the `gh` CLI uses for a lot of commands. Every skill had to switch to plain REST calls with explicit page numbers.
- **One big loop cost more than many small ones.** A laptop script that ran the builder over and over burned more tokens than separate short sessions, since context piled up. That's part of why the lanes are one issue per run.
