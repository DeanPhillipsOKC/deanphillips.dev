This is the last of three posts on governing an AI delivery pipeline. [The first](/blog/ai-governance/) covers the rules GitHub now enforces, and [the second](/blog/ai-governance-threat-model/) the threat model behind them. This one is about the afternoon they went live, and the three bugs hiding in the rules themselves.

## How a risky change merges now

For the riskiest changes (anything touching the agents' own rules, the data on the phone, or permissions), the flow ends with me. The review agent reads the change and, if it finds no blockers, turns on GitHub's auto-merge, pinned to the exact commit it reviewed. Then it asks me. I tap Approve in the GitHub app on my phone, and the change merges itself.

The pin is the whole promise. When I approve, I'm approving something the reviewer already read.

## Bug one: a merge that would never happen

The pull request that added these rules went through review first, like any other. The review agent sent it back with one blocker.

## Bug two: a commit nobody reviewed

The rules went live, and the first risky change merged itself on my approval, as designed. Then the agents opened the next one: the governance page that lists every control and its evidence. The review passed with two wording nits. A build agent fixed them and pushed one more commit.

Auto-merge stayed on.

Here it was a two-line wording fix, and I'd have been approving what was on my screen anyway. But the promise was that I only ever approve reviewed code, and a push after review broke it without any warning.

<Callout title="The pattern:">
a check that runs once, when something is switched on, isn't the same as a check that holds. If the thing it guards can change afterward, something has to watch for the change.
</Callout>

## Bug three: the fix needed fixing

That new workflow went through review too, and the reviewer found a problem in it. Here's a simplified version of the step it flagged. Can you spot it before the reviewer did?

<SpotTheBug
  prompt="Tap the line that lets an unreviewed commit sneak through."
  lines={[
    { code: '# A new commit arrived: turn auto-merge off' },
    { code: 'if ! disable_auto_merge "$PR"; then' },
    { code: '  echo "auto-merge was probably already off"', bug: true },
    { code: 'fi' },
    { code: 'comment "$PR" "Auto-merge is off. This needs a new review."' },
  ]}
  explain="Line 3 shrugs off every error, so the step reports success and posts 'Auto-merge is off' even when it isn't. A permission change or a GitHub outage would look exactly like success, and the unreviewed commit could still ride the old auto-merge in. Now the step only shrugs when auto-merge was already off. Otherwise it fails loudly."
  fix={'if ! disable_auto_merge "$PR"; then\n  if [ "$AUTO_MERGE_WAS_ON" = "true" ]; then\n    echo "Couldn\'t turn auto-merge off" >&2\n    exit 1\n  fi\nfi'}
/>

I'd let the step shrug off an error because auto-merge might already be off, which is a perfectly normal case. The reviewer's note was blunt: "a failed disable is reported as success." It was right.

Both pull requests merged that afternoon, each on my approval.

## What I took from it

- **Review the controls, not just the code.** All three bugs were in the governance work itself: a merge that would never fire, a check that only ran once, and an error treated as success. None of them would have shown up in a test of the app.
- **The rules apply to me too.** All three were in pull requests I drove from a session on my laptop, and they went through the same review as every agent's. That's where the review paid off.
- **Write down what you find.** The gap is now a row on the governance page with the workflow that closes it, so the monthly process review checks it's still there.

My favorite part is still the last one. The review bot caught a bug in the code that guards its own reviews.
