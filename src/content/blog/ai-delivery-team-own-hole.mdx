This is part 9 of a series about the AI agents that build RepBunny, a strength training app I work on around a full-time job. The [overview](/blog/ai-delivery-team/) covers the whole setup. [Part 7](/blog/ai-delivery-team-governed/) covers the rules GitHub now enforces. This part is about what happened the afternoon they went live.

## How a risky change merges now

For the riskiest changes (anything touching the agents' own rules, the data on the phone, or permissions), the flow ends with me. The review agent reads the change and, if it finds no blockers, turns on GitHub's auto-merge, pinned to the exact commit it reviewed. Then it asks me. I tap Approve in the GitHub app on my phone, and the change merges itself.

The pin is the whole promise. When I approve, I'm approving something the reviewer already read.

## The first catch: a merge that would never happen

The pull request that added these rules went through review first, like any other. The review agent sent it back with one blocker.

That would have been a quiet failure. Every risky change would sit approved and unmerged, and I'd have assumed the agents were slow.

## The second catch: a commit nobody reviewed

The rules went live, and the first risky change merged itself on my approval, as designed. Then the agents opened the next one: the governance page that lists every control and its evidence. The review passed with two wording nits. A build agent fixed them and pushed one more commit.

Auto-merge stayed on.

That's not what I expected. GitHub's auto-merge lets you name the commit you expect, and it refuses if the pull request has moved on. But GitHub checks that only once, when auto-merge is turned on. A push afterward doesn't switch it off. So if I'd approved, the new commit would have merged, and the reviewer had never read it.

Here it was a two-line wording fix, and I'd have been approving what was on my screen anyway. But the promise was that I only ever approve reviewed code, and a push after review broke it without any warning.

<Callout title="The pattern:">
a check that runs once, when something is switched on, isn't the same as a check that holds. If the thing it guards can change afterward, something has to watch for the change.
</Callout>

## The fix, and the flaw in the fix

The fix was a small workflow: whenever someone pushes to a pull request that has auto-merge on, turn auto-merge off, remove the "waiting on the owner" label, and say the change needs a new review. My approval gets dismissed on a new push anyway. That was already one of the rules.

That workflow went through review too, and the reviewer found a problem in it.

> **should-fix:** a failed disable is reported as success. Any error turning auto-merge off is swallowed, then the step still comments "auto-merge is off" and goes green, so the unreviewed commit can still ride the old auto-merge in with nobody told.

I'd written the step to shrug off an error, because auto-merge might already be off. But a real failure (a permission change, a GitHub outage) would have looked exactly like success. Now the step tolerates an error only when auto-merge was already off. Otherwise it fails loudly.

Both pull requests merged that evening, each on my approval.

## What I took from it

- **Review the controls, not just the code.** All three problems were in the governance work itself: a merge that would never fire, a check that only ran once, and an error treated as success. None of them would have shown up in a test of the app.
- **The reviewer isn't only for agents' code.** All three catches were in pull requests I drove from a session on my laptop. The rules apply to me too, and that's where they paid off.
- **Write down what you find, even the embarrassing part.** The gap is now a row on the governance page with the workflow that closes it, so the monthly process review checks it's still there.

That wraps up the governance part of the series. Two days earlier the pipeline merged on its own word. Now GitHub enforces the rules, and the reviewer found a hole in them the same day they went live.
